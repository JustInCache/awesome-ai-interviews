## What Are Reasoning Models

**Q: What is a reasoning model and how does it differ from a standard LLM?** `[B]`

A standard LLM maps input → output in a single forward pass through the generation loop. A **reasoning model** is trained to produce an extended internal **chain of thought** — often called "thinking" — before generating its final answer.

Key differences:

| Aspect | Standard LLM | Reasoning Model |
|--------|-------------|----------------|
| Output | Direct answer | Thinking trace + answer |
| Tokens generated | ~answer length | Thinking (100s–1000s) + answer |
| Latency | Fast | Slower (more tokens) |
| Accuracy on hard tasks | Lower | Significantly higher |
| Cost | Low | Higher (more tokens billed) |
| Best for | Simple Q&A, generation | Math, coding, multi-step logic |

Examples: OpenAI o1/o3, DeepSeek-R1, Claude 3.7 Sonnet (extended thinking), Gemini 2.0 Flash Thinking.

---

**Q: What is test-time compute (TTC) and why is it important?** `[B]`

Test-time compute refers to the amount of computation applied **during inference** — beyond just the forward pass to generate tokens. The core insight: you can trade more computation at inference time for better quality outputs.

Traditional scaling law: more parameters + more training data = better model.

**TTC insight** (OpenAI o1, 2024): for tasks with verifiable correct answers, **spending more tokens thinking** at inference reliably improves accuracy — similar to how a human does better on a math exam with scratch paper vs. answering immediately.

This is a fundamental shift because:
- It decouples quality from model size (a smaller model that thinks longer can beat a larger model that doesn't)
- It gives users a quality/cost/latency dial at inference time
- It opens a new scaling axis orthogonal to training

---

**Q: How do reasoning models "think"? What are thinking tokens?** `[B]`

Thinking tokens are tokens generated by the model during a private reasoning phase before producing the final response. In most implementations:

1. Model receives user query
2. Model generates a `<thinking>` block: scratch-pad reasoning, hypothesis testing, self-correction
3. Model generates the final `<answer>` based on its thinking

```
User: "If a train leaves Chicago at 9am going 60mph and another leaves NY at 10am going 80mph..."

<thinking>
Let me set up equations. Distance between Chicago and NY is ~790 miles.
Train 1: starts at t=0, position = 60t
Train 2: starts at t=1, position = 790 - 80(t-1)
They meet when: 60t = 790 - 80(t-1)
60t = 790 - 80t + 80
140t = 870
t = 6.21 hours after 9am = 3:13pm
Let me verify: Train 1 at 6.21h = 372.9 miles, Train 2 traveled 5.21h × 80 = 416.7... 
hmm 372.9 + 416.7 = 789.6 ≈ 790 ✓
</thinking>

The trains meet at approximately 3:13 PM Central Time.
```

The thinking tokens are often **not shown to users** (hidden) — they're internal scratch space. This has implications for API costs (you may be billed for invisible tokens).

## Test-Time Compute Scaling

**Q: What are the main approaches to scaling test-time compute?** `[I]`

Three primary TTC strategies:

**1. Sequential thinking (chain-of-thought)**
The model generates a long thinking trace before answering. Simple and effective. All current reasoning models use this as the foundation.

**2. Self-consistency / majority voting**
Generate N independent answers (N parallel samples), pick the most common. Works well when:
- You can sample cheaply
- Correct answers cluster together in output space
- Trade-off: N× cost for sublinear quality gains

**3. Search / tree of thoughts**
The model explores multiple reasoning paths, evaluating partial solutions and backtracking when stuck. More complex but more powerful for hard combinatorial problems.

```
                    Root (problem)
                   /    |    \
              Path A  Path B  Path C
             /    \         \
          A1      A2         C1
        [dead]  [continue]  [best]
```

MCTS (Monte Carlo Tree Search) is used in some advanced reasoning systems — the model acts as both the policy (which moves to explore) and the value function (which paths look promising).

---

**Q: What is the "scaling law" for test-time compute?** `[I]`

OpenAI's work on o1 showed that reasoning model performance on benchmarks like AIME (math competition) scales roughly **log-linearly** with the number of thinking tokens:

- More thinking tokens → better performance
- Diminishing returns set in, but the curve is remarkably consistent
- At some tasks (e.g. hard math), even 10,000 thinking tokens help vs. 100

The practical implication: you can tune thinking budget at inference time to control the quality/cost trade-off. This is exposed as the `thinking_budget` or `reasoning_effort` parameter in some APIs.

**Important caveat**: TTC scaling only works for tasks with **verifiable structure** — math, coding, logic puzzles. For open-ended creative tasks or tasks requiring world knowledge, more thinking doesn't reliably help.

---

**Q: What is "compute-optimal" inference?** `[I]`

Chinchilla scaling laws gave us compute-optimal training (match parameters to data to training FLOPS). The analogous question for inference: **given a fixed inference budget, should you use a larger model with no thinking, or a smaller model with extended thinking?**

Empirical finding: for reasoning tasks, a smaller reasoning model with TTC budget often outperforms a larger standard model at the same total FLOP cost. This makes smaller reasoning models attractive for production — lower memory, lower serving cost, tunable via thinking budget.

## Training Methodology

**Q: How are reasoning models trained? What is RLVR?** `[I]`

Reasoning models are typically trained via **Reinforcement Learning with Verifiable Rewards (RLVR)**:

1. **Start with a capable base model** (e.g. LLaMA, Qwen, or an internal model)
2. **Generate rollouts**: model produces thinking trace + answer for many problems
3. **Verify correctness**: for math problems, check final answer against ground truth. For code, run tests. **No human labeler needed** — the reward is binary (correct/incorrect).
4. **RL update (GRPO, PPO)**: reinforce trajectories that led to correct answers; penalize incorrect ones
5. **Emergent behavior**: the model learns to use thinking tokens for complex problems, developing strategies like backtracking, self-checking, and decomposing

**Why RLVR works**: unlike RLHF which requires human preference labels, RLVR uses **ground truth verifiers** — math has objectively correct answers. This makes data collection cheap and scalable.

DeepSeek-R1 demonstrated that this approach works with open-source base models, achieving o1-comparable performance.

---

**Q: What is the "aha moment" in reasoning model training?** `[I]`

During RLVR training, researchers observe an emergent phenomenon: models spontaneously develop **self-reflection behaviors** — including re-examining their work with phrases like "wait, let me reconsider" or "actually that's wrong."

This wasn't explicitly trained — it emerged from the RL signal of getting math problems right. The model learned that reconsidering intermediate steps improves its reward.

This suggests the thinking trace isn't just outputting a pre-formed solution — it's actively being used for computation. The model is genuinely "thinking" in a meaningful sense, not just pattern-matching.

---

**Q: What is GRPO and how does it differ from PPO for reasoning model training?** `[A]`

Both PPO (Proximal Policy Optimization) and GRPO (Group Relative Policy Optimization) are RL algorithms used for reasoning model training.

**PPO**:
- Requires a separate value/critic network to estimate baseline rewards
- Stable but memory-intensive (two large models in memory)
- Used in original RLHF work and OpenAI's internal training

**GRPO** (DeepSeek's innovation):
- Eliminates the critic model by using **group-based baselines**
- For each problem, generate a group of K responses, compute mean reward as baseline
- Policy update = how much better/worse than the group average
- Half the memory of PPO, similar or better training stability

```
# GRPO intuition
rewards = [correct, correct, wrong, correct, wrong]  # K=5 responses
baseline = mean(rewards) = 0.6
advantages = rewards - baseline = [0.4, 0.4, -0.6, 0.4, -0.6]
# Reinforce responses that beat the group; penalize those that don't
```

GRPO is now the dominant approach for open-source reasoning model training.

## Process Reward Models

**Q: What is a Process Reward Model (PRM) and how does it differ from an Outcome Reward Model (ORM)?** `[I]`

Both PRMs and ORMs are used to score reasoning model outputs, but they differ in granularity:

**Outcome Reward Model (ORM)**:
- Scores only the **final answer**: correct = 1, wrong = 0 (or soft reward)
- Simple and cheap to train
- Limited: provides no signal about which steps in the reasoning were good/bad

**Process Reward Model (PRM)**:
- Scores each **intermediate reasoning step**
- Trained on human (or AI) labels of which steps are logically correct
- Enables more fine-grained RL training and better search

```
Step 1: "Let x = speed of train A" → ✓ score: 0.95
Step 2: "Distance = speed × time, so x·t = 370" → ✓ score: 0.91
Step 3: "Therefore x = 370/4 = 92.5" → ✗ score: 0.2  (wrong operation)
Step 4: "So train A travels 92.5 mph" → ✗ score: 0.1
```

PRMs enable **beam search at inference time**: generate multiple reasoning paths, use the PRM to score partial paths, and prune bad branches early — before they lead to wrong answers.

---

**Q: How are PRMs trained?** `[A]`

PRM training requires labeled reasoning steps — significantly more expensive than outcome labels:

**Human labeling**: annotators rate each step as correct/neutral/incorrect. Gold standard but expensive (~$10–100 per problem for multi-step math).

**Process reward model distillation (Math-Shepherd approach)**: 
1. For each step in a reasoning trace, complete the rest of the problem many times (Monte Carlo rollouts)
2. If the completion frequently reaches the correct answer from this step → the step is likely correct
3. Use these automated labels to train the PRM

This enables scalable PRM training without human step labels. The quality is lower than human labels but tractable at scale.

## Thinking Tokens & Budgets

**Q: How do thinking token budgets work in production APIs?** `[I]`

Major API providers expose thinking budget controls:

**OpenAI (o-series)**: `reasoning_effort` parameter — `low`, `medium`, `high`. Maps to internal thinking token limits (~1K, ~10K, ~32K tokens). Higher effort = better quality, higher cost, higher latency.

**Anthropic (Claude 3.7)**: `thinking: {type: "enabled", budget_tokens: N}` where N is max thinking tokens. Thinking tokens are billed at normal rates.

**Practical guidance**:
- **Use low/medium for most production queries** — the marginal quality gain from high effort is often small for real-world tasks (not competition math)
- **Measure, don't assume** — run your actual task distribution against different thinking budgets. The optimal setting is task-dependent.
- **Watch for billing surprises** — on hidden-thinking APIs, you may be paying for 5,000 thinking tokens per query invisibly

---

**Q: What is "thinking token overflow" and how do you handle it?** `[A]`

Thinking token overflow occurs when the model's thinking trace consumes most or all of the context window before reaching a conclusion. This can happen with:
- Very complex problems requiring extensive scratch work
- Infinite loops in reasoning (model keeps reconsidering)
- Problems outside the model's ability (model flails)

**Engineering mitigations**:
1. **Set explicit budget limits** — cap thinking tokens to 20–30% of context window
2. **Detect incomplete thinking** — monitor if `</thinking>` is generated before budget exhaustion; if not, the answer may be unreliable
3. **Graceful degradation** — if thinking runs out, fall back to a standard model response
4. **Problem decomposition** — break complex problems into sub-problems, each solvable within budget

## When to Use Reasoning Models

**Q: How do you decide whether to use a reasoning model or a standard model in a production system?** `[I]`

Use a **decision framework**:

**Step 1: Is the task structure-verifiable?**
- Can you automatically check if the output is correct? (math result, code that compiles and passes tests, valid JSON)
- If yes → reasoning model helps
- If no → reasoning model offers little benefit

**Step 2: What's the difficulty distribution?**
- If 90% of queries are easy, use **model routing**: classify query difficulty first, route hard queries to reasoning model, easy queries to fast model
- Saves 80–90% of cost vs. always using reasoning model

**Step 3: What's your latency constraint?**
- Reasoning models add 2–10× latency (more tokens to generate)
- If P99 latency < 1s is required: reasoning models likely not viable for synchronous use
- Consider async: queue complex tasks, return results via webhook

**Step 4: Cost calculation**
- Benchmark your actual task on o1/o3-mini/R1 with different thinking budgets
- Calculate quality improvement × business value vs. marginal cost
- Often: R1/o3-mini with low thinking budget > standard GPT-4o on hard tasks at comparable cost

## Production & Engineering

**Q: How do you build a system that routes between reasoning and standard models?** `[I]`

```python
# Model routing pseudocode
def route_query(query: str, context: dict) -> str:
    # Fast classifier to estimate complexity
    complexity_score = complexity_classifier(query)
    
    # Rule-based routing
    if any(keyword in query.lower() for keyword in ["calculate", "prove", "debug", "optimize algorithm"]):
        complexity_score = max(complexity_score, 0.7)
    
    if complexity_score >= 0.8:
        # Hard query: use reasoning model
        return call_o3_mini(query, reasoning_effort="medium")
    elif complexity_score >= 0.5:
        # Medium query: use standard model with CoT prompt
        return call_gpt4o(query, system="Think step by step before answering.")
    else:
        # Simple query: fast model
        return call_gpt4o_mini(query)
```

**Key metrics to track**:
- Route distribution (what % goes to each tier)
- Quality by route (LLM-as-judge on sampled outputs)
- Cost per query by route
- User satisfaction signals by route

**Q: How do you evaluate whether a reasoning model is actually helping in your use case?** `[I]`

Don't rely on benchmark scores (AIME, HumanEval) — they measure academic performance, not production performance.

**Evaluation process**:
1. **Collect 100–200 representative production queries** — queries that are failing or marginal with your current model
2. **Get ground truth answers** — either human-labeled or auto-verifiable
3. **Run head-to-head**: reasoning model vs. current model on same queries
4. **Measure**: accuracy, latency, cost, + qualitative inspection of edge cases
5. **Calculate ROI**: (accuracy improvement × business value per correct answer) vs. (marginal cost per query)

**Common finding**: reasoning models help 10–30% of "hard" queries but add 5–10× cost. The key question is whether your application is dominated by hard queries.

---

**Q: What are common failure modes of reasoning models in production?** `[A]`

**1. Overthinking on easy queries**
Model generates 2,000 thinking tokens to answer "What's 2+2?" — wastes tokens, adds latency, and sometimes makes the model second-guess correct answers.

**2. Reasoning hallucinations**
The model produces confident-sounding reasoning steps that are factually wrong. Unlike standard hallucinations, these are harder to detect because the *format* looks rigorous.

**3. Prompt sensitivity**
Reasoning models can be more sensitive to prompt formatting — slight changes to system prompts can cause dramatically different thinking strategies.

**4. Long reasoning context issues**
For very long problems, the thinking trace can become incoherent as earlier reasoning context fades from attention.

**5. Latency unpredictability**
Thinking length varies widely — same query can take 200 or 2,000 thinking tokens depending on how the model "feels" about it. Set `max_tokens` and handle timeouts.

## Evaluation & Benchmarks

**Q: What benchmarks are used to evaluate reasoning models?** `[I]`

| Benchmark | Domain | Why It's Used |
|-----------|--------|---------------|
| **AIME** | Math (competition) | Hard problems requiring multi-step exact reasoning; o1 was first model to score meaningfully |
| **MATH-500** | Math (diverse) | Broad math benchmark; saturating for best models |
| **AMC 2023** | Math (competition) | Similar to AIME, slightly easier |
| **HumanEval / LiveCodeBench** | Coding | Code generation and debugging |
| **SWE-bench** | Software engineering | Real GitHub issues; requires understanding codebases |
| **GPQA Diamond** | PhD-level science | Expert-level questions in biology, chemistry, physics |
| **ARC-AGI** | Abstract reasoning | Visual pattern completion; tests novel reasoning |
| **FrontierMath** | Advanced math | New dataset; problems that require novel approaches |

**Warning for practitioners**: all benchmarks saturate over time and can be gamed. LLM providers optimize for benchmark scores, sometimes at the expense of general capability. Always evaluate on your own held-out distribution.

**Q: How do you measure reasoning quality beyond final answer accuracy?** `[A]`

Final answer accuracy misses important nuances. Better evaluation approaches:

**Step validity scoring**: use a PRM (or human labelers) to check if intermediate steps are logically valid, even if the final answer is wrong.

**Faithfulness**: does the final answer actually follow from the thinking trace? (Models sometimes "skip" to correct answers without using their reasoning.)

**Efficiency**: how many tokens did the model use relative to the minimum needed? Bloated reasoning is a quality signal issue.

**Consistency**: run the same problem 5 times with temperature > 0 — how often does the model reach the same conclusion? High variance = low confidence.

**Robustness**: slightly rephrase the problem — does the reasoning hold up? Or does the answer flip?

```python
# Consistency evaluation
answers = [model.answer(problem, temperature=0.7) for _ in range(5)]
consistency_score = max(set(answers), key=answers.count) / len(answers)
# consistency_score = 1.0 → always same answer (high confidence)
# consistency_score = 0.2 → model is guessing
```
